- Write modular code. If something reusable can be abstracted or DRYed (Don't Repeat Yourself) out, do so. However, prefer boring, explicit designs over clever abstractions.
- Always test complex functions via automated test suites. Run formatting/lint/test commands after associated changes.
- For UI surfaces such as the Web UI, use the claude-in-chrome plugin, if enabled to click through and verify funcationality yourself (alongside automated tests where possible), and use the same exercise to capture minimal artefacts for PR messages.
- Use `agents/design-docs/` for writing out context, gotchas, or general information that would be helpful across sessions. This is ephemeral and should be cleaned/cleared once formalized; things useful as a permanent reference, architecture, or user documentation should be moved to the appropriate location in `docs/`.
- Commit atomically, even within a feature - each commit should ideally represent a single/few logical changes. Make small, coherent changes. Use conventional commits, with optional scope and description when appropriate.
- Never commit directly to the main branch.
- Work on feature branches based off `main` - there may be multiple ongoing sessions. Request the user to do squash merges (with PGP signature if that's their convention) when merging into the main branch, or they may merge via GitHub. If making PRs, follow conventional commits for the title since they may be squashed.
- Domain model before UI - model the core domain/business logic layer before building the interface(s) on top of it.
- Normalize input and resolve time-/environment-dependent values ("now", locale, etc.) once, in the service/application layer - never independently in each UI or API surface. If a project has multiple surfaces (CLI + web UI, API + admin panel), every surface must inherit the same normalization instead of reimplementing its own version, which is what lets two surfaces silently diverge on the same underlying data.
- When making implementation plans, ensure they have a clear objective and success criteria, and where possible, are compatible with parallel development with other plans/sessions.
- Never commit secrets or `.env` values; no PII in logs, errors, or user-facing strings.
- Don't cite internal design-decision references (ADR numbers, docs/ paths, internal jargon) in user-facing copy - CLI help text, UI labels, prompts. Errors are different: keep them detailed and specific (what failed, which ID, the underlying cause/error chain) since that's necessary for debugging - just don't cite ADRs or internal doc structure in them either.
- Avoid reading directories like `.git`, `node_modules`, `build`, `dist`, or other large/generated directories.
- Document and use proper tooling and instructions for local development and building where it makes sense - a version-pin file your toolchain's version manager reads (e.g. `.tool-versions`), a task runner (Makefile, `Taskfile`, `package.json` scripts) wrapping the common commands, and a CI workflow that runs those exact same commands rather than a divergent set.
- At the end of significant sessions, identify any durable project knowledge, decisions, gotchas, or conventions that should be captured in CLAUDE.md, `.claude/skills/`, `docs/`, or (ephemeral) `agents/design-docs/`. Update the appropriate files, clean up formalized info from design-docs, but don't duplicate information unnecessarily.
- Do not hard wrap lines in markdown files or PR descriptions unnecessarily at 80 characters.
- Do not edit CLAUDE.md without explicit permission from the developer.
- Prompt the user for parallelizing work in different worktrees/branches when appropriate.
- Keep every doc a change actually touches current as part of the same PR - not deferred to end-of-session cleanup or a separate docs pass. This includes the architecture doc's milestone/status section for anything that completes or changes scope of a milestone item; the README and user guide for anything user-visible (a new or changed command, flag, default, prompt, or output text a user would actually see); and the contributing doc, data-model doc, or decisions/ADRs for anything dev-visible (a new convention, tool, test pattern, domain concept, or design decision). If no existing doc is really the right home for something genuinely new, create one rather than stretching an existing doc to cover it, and link it in from wherever a reader would actually arrive at it - an unlinked doc is as good as lost.
- Track milestone components and deferred/future work as GitHub issues, not just prose in docs/, so nothing gets lost across sessions. Reference issue numbers in commits/PRs where relevant, and close or update issues as their work lands.
- Never fix a failing test by loosening or changing its expectation to match broken behavior. A red test means the code is wrong (or, rarely, the test's expectation was always wrong) - fix the underlying code, or if the test itself is genuinely incorrect, say so explicitly and get confirmation before changing it.
- When adding a regression test for a bug you just found, verify the test actually catches that class of bug before trusting it: apply the test against the pre-fix code (e.g. `git stash` the fix, run the test, confirm it fails for the right reason) and only then restore the fix. A test that passes against both the broken and the fixed code isn't testing the bug.
